## Godot 和 LLM 的组合技……

说实话，之前我一直觉得 Godot 这种万物皆文本的模式十分适合当前 LLM 辅助编程的流程，而且其编辑器也确实能很好地显示各种修改，所以我这一年基本没亲自编辑过 tscn

毕竟，这能出什么问题呢？

最糟糕的问题……导出后功能变了。

同一个 .tscn 文件里的合法属性，直接加载时生效，重新打包时却被静默丢弃。

- Control::_validate_property()：直接父节点是 Container 时，pivot_offset、rotation、scale 等属性的 usage 被设置为 EDITOR | READ_ONLY，不含 STORAGE。
- SceneState::_parse_node()：重新打包节点时，缺少 PROPERTY_USAGE_STORAGE 的普通属性会被跳过。

于是形成了这么一条荒唐的路径：
- LLM 直接在 tscn 里给 Container 的子节点写了 pivot_offset
- 测试运行时编辑器正常加载了 pivot_offset，一切正常
- 导出时 pivot_offset 被跳过，导致导出后的 scn 里 pivot_offset 丢了
- 导出后的构建在运行时 pivot_offset 直接成为 (0,0)，进而和测试时用编辑器运行的表现完全不同

要说我学到了什么……那好像也没有学到什么，也就是在 godot skill 里加一条“别在 Container 节点的直接子节点下写 pivot_offset、rotation、scale 等属性，它们在导出时会被忽略，导致导出结果和测试运行不一致”

毕竟这纯粹是工具问题，而我也确实想不到什么办法能以可接受的代价在未来规避类似的问题……

## windows 路径长度限制的各种问题

### 担心 windows 路径长度限制大改了构建
有些担心玩家因为 code oss 和 python 运行时的依赖库撞上 windows 路径长度限制。

于是做了套这么个机制：

发布时，把 runtime 打成 zip。在玩家启动游戏、选定语言后，提供对应语言的相关说明“计算节点部署设备存在路径长度限制，是否启用长路径支持？”

然后在旁边放一个 tooltip 写着
```
给计算节点：启用长路径支持不会带来任何性能或者安全性问题，这单纯是上纪元那个叫 Windows 的操作系统留下的兼容包袱。如果不启用这个支持，可能会导致计算节点的客户端无法完整加载进而导致运行错误。
——用户 ghostine
```

玩家如果允许，那就启用长路径。玩家如果拒绝，那就跳过启用长路径直接尝试进行解压但是如果出现长路径导致失败那就提示不行并且退出，玩家下次仍然能看到这个界面。

### 改完后发现卵用没有

然后发现死活无法正常启动基于 python 的各种 agent 子进程。

折腾了到了周日，才发现是因为我给虚拟机分配的资源太少（最低的 1cpu 2G 内存），以至于资源扫描阶段 cpu 撑满了无法及时启动子进程并握手。分 4cpu 8G 内存后问题就消失了

然后又发现解压在一些 cpu 不是很好的设备上属实算不上快，恐怕玩家难以接受

而进一步调研后发现，这个长路径有一堆令人无语的特性

| **层级**           | **路径长度限制**             | **是否受 LongPathsEnabled 影响**        |
| ------------------ | ---------------------------- | --------------------------------------- |
| NTFS 文件系统      | 约 32,767 字符的扩展路径上限 | 不受影响                                |
| Win32 文件 API     | 默认 260 字符                | 部分 API 可解除限制，但要求程序声明支持 |
| Windows 资源管理器 | 仍可能卡在 260 字符          | **开启也不能保证解决**                  |

结果就是，假设一个压缩包包含 `D:\ProxyOS\runtime\Lib\site-packages\...\very_long_filename.py` 这种超长路径，那么：

1. `tar.exe` 使用支持长路径的文件操作，可以成功创建它。
2. NTFS 接受这个文件，并正常存储。
3. 玩家通过资源管理器复制整个 `runtime` 目录。
4. 资源管理器遇到深层文件，发现完整路径超过自身支持范围，于是报错。

解压成功、文件真实存在、资源管理器却复制不了——真他妈绝了

所以我放弃了，把 runtime 解包的流程全删了，改成了 build 后生成一个 cfg，里面记录可接受的父目录路径长度。当玩家启动游戏选完语言后，如果发现玩家放得太深，就会问玩家要不要帮开 LongPathsEnabled 来避免问题，并建议移动游戏安装位置到较浅的目录。
