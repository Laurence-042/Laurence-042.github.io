## 重写了剧本系统

突然冒出来一个交易后一直循环触发事件的 bug

然后研究了下，发现链条是
- 玩家触发交易
- 交易商品有 hook，调用
- 调用 hook 会设置一个存档变量
- 这个存档变量触发了另一个与其无关的事件的条件检查，然后因为错误的检查机制误触发了
- 无关事件的误触发里再次设置了变量，再次触发

这个的核心问题就是之前验证的时候寻思先搓个能跑的，然后再优化性能，结果就把这事忘了。

结果就导致变量更新会触发其他要检查变量的事件的条件检查。

进一步分析后发现，当时实现得根本就是一坨。

[那时候](./proxyos-weekly-073) 我应该是刚开始使用 codex，当时它实在过于不遵循指令但偏偏十分能理解目标，经常搞出不符合指令、代码架构一坨、但能满足目标的实现。当时我也正好在实验各种 llm 辅助编程范式，于是我就寻思试试正经当个 SE，避免自己在审它代码时爆血管，只管模块输入输出没问题就行。

于是，我就在处理这个十分麻烦的剧本系统时给定了输入输出数据格式、一些我觉得覆盖比较全的供其自我验证的流程，就让它干了。干完后确实符合模块级要求，我也就给这个化粪池盖了盖子，把它提交了。

然后今天化粪池就爆了。

技术债终究是得偿还的，于是就自己做了系统设计，然后给 codex 设计文稿、纠正 codex 尝试把设计往旧系统上套的错误理解、纠正 codex 尝试把设计解释为对旧系统的概念说明的错误理解、怒喷 codex 不要把我描述的通用规则解释成某种屎山上的特例而是应该按照通用规则彻底重构、检视 codex 代码后力竭地质疑它为啥要把好好的 condition 自治的信号侦听搞成中心化的映射表、被 gdscript 类型系统的神秘小特性背刺……

于是一天过去了

## 界面原型

“让 codex 用网页做原型，再将其迁移到 godot”相比于“让 codex 直接做 godot 场景”给出的结果质量似乎有显著提升，这可能是训练语料的数量差异导致的。毕竟严格来说 llm 没有内置的“我想象这个界面应该是啥样，然后我把它翻译成代码”的这么个流程，而是更接近“我想一些这个界面的指标，然后按照指标的同时稍微凭直觉自由发挥下”，自然相同的要求在不同的前端设计语言中会表现得不同。

“让 llm 在训练良好的领域做原型，然后进行迁移”这个小 trick 应该还是有点用的。
