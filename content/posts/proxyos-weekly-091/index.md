# 主要进展内容/本期关键判断点

> 我做出了哪些「如果错了也要付代价」的判断？

## 优化了项目的 AGENTS.md 管理

zcode 只会读项目目录及其祖先目录里的 AGENTS.md，不会读项目内模块的 AGENTS.md，添加了一个自动脚本来自动添加与更新项目 AGENTS.md 里的模块 AGENTS.md 索引，提高 LLM 工作前读相关 AGENTS.md 的概率。

诚然，这玩意并不能保证 LLM 读，而且从定位上看这更应该通过插件做进 zcode 的能力里来保证 LLM 读，但是我觉得现在这样也够用。而且这么做之后所有 harness 只要读项目 AGENTS.md 就都会自动适配，兼容性也会更好。

## 重构了脚本预验证系统

之前的脚本验证系统本质上是
- vscode 的 post 任务调用预设 python 脚本给 godot 侧上报调试的文件
- godot 侧将其根据任务需求配置的脚本路径，确认玩家调试的文件和哪个需求关联
- 如果找到关联，进行自动验证。如果过了，就让桌宠提示玩家可以提交给对应任务了

但感觉太挫了，于是这期改成了
- vscode 的 post 任务调用预设 python 脚本给 godot 侧上报调试的文件
- godot 侧对每个正在执行的任务的脚本验证需求验证这个上报的文件
- 如果哪个过了，那么就让桌宠提示玩家可以提交给对应任务了

这主要是考虑到这个游戏里的脚本编写任务都不会是重计算量的，并发 6 秒足够。如果死循环且验证器也没拦住，导致 worker 进程被干掉重启，那么验证一个任务和验证多个任务的死循环风险其实是一样的。所以这个修改应该是净收益

## 大改了轻聊的插件系统，现在其不再依赖 stdio，而是专用 ipc

之前觉得 stdio 消息处理少、吞吐量大，所以用 stdio 做了插件的文本处理交互。但是实测发现效率非常低下，检查后我认为是 stdio 的频繁 flush 和双向通信的处理复杂导致的

而基于 websocket 的 ipc 反而十分适合轻聊的这种大量短消息快速并发处理的任务，所以就改成用 ipc 了
